# 生产部署与扩展

本页明确区分“仓库当前已经实现”与“面向公网或多设备时需要建设”。不要把后续建议理解为项目已具备的能力。

## 当前已经实现

- 一台 Glass3 作为发送端，一个 PC 浏览器作为接收端。
- Glass SDK NV21/PCM 采集与 WebRTC 单向音视频发送。
- 同一可互访局域网内使用 host ICE candidate 直连。
- Node.js 提供静态页面、健康检查和 WebSocket 信令。
- 固定房间或用户输入 roomId，基础角色配对、状态展示和有限重连。
- 浏览器不采集本地媒体，Node.js 不承载、不保存媒体。

当前实现没有账号认证、设备授权、TLS、STUN/TURN、SFU、持久化房间、集群状态共享、服务端录制和云端监控。它适合体验、接口验证和局域网单路业务原型。

## 面向公网必须增加

### 身份与房间授权

不要把可猜的 roomId 当作安全凭证。业务服务应给登录用户和已登记设备签发短期令牌，令牌至少绑定设备 ID、房间 ID、角色、签发时间和过期时间。信令服务在加入房间前校验令牌，并限制一个身份可创建的连接数。

### HTTPS 与 WSS

把网页和 WebSocket 放到受信任域名，通过反向代理终止 TLS，只开放 HTTPS/WSS。Android 生产配置使用 `wss://`，移除全局明文许可。证书到期时间应纳入监控。

### STUN 与 TURN

公网、跨网段、企业防火墙或运营商 NAT 下，host candidate 通常不够。配置 STUN 用于发现公网映射，部署带鉴权的 TURN 作为无法直连时的媒体中继。TURN 需要规划 UDP/TCP/TLS 端口、带宽、地域和费用，并监控分配成功率。

### 反向代理与防火墙

反向代理必须支持 WebSocket Upgrade、合理的空闲超时和真实客户端地址传递。防火墙只开放所需的 HTTPS/WSS 和 TURN 端口；Node.js 业务端口可仅监听内网，由代理访问。

### 限流与滥用防护

按 IP、账号、设备、房间限制连接频率和并发数，限制信令消息大小与发送频率，拒绝未知消息类型。认证失败、频繁重连和超限需要审计，但日志不能记录令牌和完整 SDP 中可能不必要的敏感信息。

### 日志、保留与监控

生产日志至少关联请求 ID、设备 ID 的脱敏值、房间 ID 的脱敏值、状态转换、错误码和耗时。明确日志保留期限和访问权限。监控活跃连接数、协商成功率、首帧时间、音视频码率、丢包、RTT、重连率、TURN 使用率、CPU、内存和事件循环延迟，并配置告警阈值。

## 多设备或多观看者需要增加

当前服务的内存房间适合单发送端、单接收端。要支持多个设备，应增加持久化设备/房间模型、明确成员角色、连接踢出和状态恢复；信令服务横向扩容时需要 Redis 等共享房间与消息通道，并保证粘性连接或正确路由。

一个眼镜对应多个观看者时，不建议眼镜建立多条上行 PeerConnection。应引入 SFU，让眼镜只上传一路，SFU 转发给多个浏览器。SFU 方案还需处理 simulcast/SVC、订阅权限、带宽估计、关键帧请求、录制和区域调度。

## 推荐上线顺序

1. 先在目标网络完成单眼镜、单浏览器长稳测试。
2. 增加域名、HTTPS/WSS、身份认证与授权。
3. 部署 STUN/TURN，并验证 Wi-Fi、蜂窝网、VPN 和严格 NAT。
4. 建立限流、结构化日志、指标、告警和保留策略。
5. 确认确有多观看者需求后再引入 SFU，不把复杂度提前放进简单客户场景。

以上生产能力需要结合客户现有账号、网关、证书和运维体系设计，本仓库只提供清晰的改造边界。
